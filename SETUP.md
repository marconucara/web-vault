# WebVault — onboarding prompt (any vault)

Hand this file to a coding agent working **inside a Markdown vault** to add a
web client to that vault. It is a self-contained spec: the agent reads it and
performs the setup end-to-end — no interactive wizard, no `npx` prompts. This is
the intended setup path (see `adr/0029-cli-setup-and-distribution.md`).

> **You are the agent.** Work from the vault root. You will create one new
> folder, `.web/`, holding *only configuration*; the application and build
> pipeline stay inside the `web-vault` package pulled in as a dependency. Do not
> copy app code into the vault.

**Scaffolding needs no local toolchain.** Creating `.web/` is just writing text
files — no Node, Yarn, or install required, so anyone can be onboarded even
without a developer environment. Node and Yarn are needed only to *test the site
locally*, which is optional (step 3). Deploying (step 4) runs the build in the
cloud, so it needs no local toolchain either.

---

## 0. What WebVault is (context you need)

A static React/Vite web client that reads the vault **at build time** and serves
it, with an in-browser editor that commits changes back through a Cloudflare
Pages Function. It works with generic Markdown vaults and is compatible with
[Tolaria](https://github.com/refactoringhq/tolaria) and Obsidian vaults.

The shell you scaffold (`.web/`) is a thin consumer: `package.json` scripts wrap
the package's `wv` CLI, and everything else is config. Generated content
(`.wv/`), Functions (`functions/`), and `dist/` are build artifacts — gitignored,
never hand-edited.

## 1. Preconditions

Confirm, and stop with a clear message if either fails:

1. **You are at the vault root** — the directory that holds the `.md` notes you
   want to serve. If not, ask the user for the vault path and `cd` there first.
2. **The vault has at least one `.md` note.** Optional `views/*.yml` (saved
   views) and `attachments/` (media) are picked up if present but not required.

That is all the scaffolding needs. A git remote is required only for editing and
deploy (both resolve the target repo from the vault's `origin`), not for
scaffolding or local viewing.

## 2. Scaffold `.web/` (no toolchain required)

Create `.web/` at the vault root and write the files below verbatim, adjusting
only the values called out as vault-specific. `.web` sits **inside** the vault,
so the build finds the vault at `../` automatically (override with `VAULT_DIR`
if you place the shell elsewhere).

### `.web/package.json`

`name` is arbitrary. Pin the dependency to a released tag of the public repo.

```json
{
  "name": "vault-web",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "wv dev",
    "build": "wv build",
    "preview": "wv preview",
    "gen": "wv gen",
    "maps:genkey": "wv genkey"
  },
  "dependencies": {
    "web-vault": "github:marconucara/web-vault#v0.10.0"
  },
  "packageManager": "yarn@4.5.3+sha512.3003a14012e2987072d244c720506549c1aab73ee728208f1b2580a9fd67b92d61ba6b08fe93f6dce68fd771e3af1e59a0afa28dd242dd0940d73b95fedd4e90"
}
```

### `.web/.yarnrc.yml`

```yaml
# The CLI relies on real node_modules symlink resolution
# (--preserve-symlinks), which Yarn PnP breaks.
nodeLinker: node-modules

# Let an install update yarn.lock instead of refusing to run. CI enables
# immutable installs by default, which makes the cloud build fail the moment the
# web-vault pin changes (step 5) — the lockfile still names the old tag, and only
# a real install can rewrite it correctly. There is one direct dependency here,
# pinned to a tag, so there is little for the immutable check to catch.
enableImmutableInstalls: false
```

```
22
```

### `.web/wrangler.toml`

Cloudflare Pages deploy config. Harmless if the user never deploys. Set `name`
to the Pages project name (default it to the vault folder name; the user can
change it at deploy time). Everything else is boilerplate.

```toml
# Cloudflare Pages configuration, versioned in the repo.
#
# Holds ONLY non-secret, deploy-portable settings. Secrets (GITHUB_TOKEN) and the
# build-time keys (MAP_CACHE_KEY / SITE_URL) stay as Pages env vars/secrets.

# Must match the Cloudflare Pages project name, or the git build can fail.
name = "your-vault"

# Static build output produced by `yarn build`.
pages_build_output_dir = "dist"

# Runtime API version for the /api/* Pages Functions.
compatibility_date = "2026-07-01"

# The Functions use only Web APIs, no Node builtins, so nodejs_compat is left
# OFF. Enable it only if a Function later imports a `node:` module.
# compatibility_flags = ["nodejs_compat"]

# The commit Function auto-detects the vault repo from its git remote. To pin it
# explicitly (or in a fork), set it here instead:
# [vars]
# GITHUB_REPO = "you/your-vault"
```

The response-header rules (`_headers`) are **not** scaffolded: the build
generates `dist/_headers` for you. The optional Maps link cache uses a `.env`
you can create later (`yarn maps:genkey`); it is not needed for setup.

### `.web/AGENTS.md`

So future agents treat this folder as a config-only deployment shell, not a
notes vault.

```markdown
# AGENTS.md — .web (web-vault consumer)

`.web` is the deployment shell for this vault's web client. It is **not** a notes
vault: the vault's own note conventions (wikilinks, types, views, frontmatter) do
**not** apply here.

The application, build pipeline, and scripts live in the separate `web-vault`
package (a dependency in `package.json`). This folder holds **only
configuration** — change config here; app changes go to the `web-vault` package.

## How to use it

- `yarn dev` — local dev server
- `yarn build` — full static build into `./dist`
- `yarn preview` — serve the build

All wrap the `web-vault` `wv` CLI. Generated content (`.wv/`), Functions
(`functions/`), and `dist/` are build artifacts (gitignored) — never edit or
commit them by hand.

## Rules

- Everything user-facing in the client is **English** (only vault note content
  may be non-English).
- Deploy **behind Cloudflare Access**; only `/shared/*` is public. Never expose
  the private vault.
```

### `.web/CLAUDE.md`

```markdown
@AGENTS.md

Claude Code compatibility shim for the `.web` subproject. The instructions live
in `.web/AGENTS.md`. Do not apply the vault's note conventions here.
```

Scaffolding is now complete. Commit `.web/` to the vault repo. The user can stop
here and hand deploy to the cloud (step 4), or test locally first (step 3).

## 3. Test locally (optional — needs Node + Yarn)

Only for previewing the site on the user's machine before deploying. **Check the
toolchain first:**

- `node --version` → **22** and `yarn --version` → **4.x** (install Yarn 4 via
  `corepack enable` if missing).

If either is missing, tell the user plainly: *local testing needs Node 22 and
Yarn 4; without them, skip to deploy (step 4), which builds in the cloud.* Do not
try to install a system toolchain unless the user asks.

If present, from inside `.web/`:

```sh
yarn install     # pulls web-vault from the public repo
yarn dev         # generates content, then starts the Vite dev server
```

Then verify: `yarn dev` prints a local URL; opening it shows the note list and a
note opens with its content (and any `views/*.yml` as saved views). `yarn build`
completes and produces a coherent `.web/dist/`. If content is empty, confirm
`.web/` is **inside** the vault (so `../` is the vault root) or set `VAULT_DIR`.

## 4. Deploy (optional — do only if the user asks)

Publishing is optional and builds in the cloud (no local toolchain). The setup
is documented once in [`DEPLOY.md`](DEPLOY.md) — follow it to add the deploy
config to `.web/`, create the Cloudflare Pages project, and set the secrets and
access. Do not duplicate those steps here.

## 5. Upgrading later (nothing to do now)

Nothing to set up — this is here so you know the pin above is a starting point,
not something the user will have to maintain by hand.

A deployed WebVault marks its version indicator when a newer version is
published, and a deployment that can write (one with a GitHub token configured)
offers to update itself from that notice. Accepting it commits the new pin to
`.web/package.json` on the deployment's branch, which rebuilds and reinstalls at
that version — the same commit-and-rebuild cycle as editing a note.

A deployment with no token configured shows the published version and links to
it instead, since it has no way to commit the change; there the pin is still
edited by hand. Local development also stays manual: `wv dev` writes the new pin
to disk, and the reinstall is the user's to run.

The upgrade commits the pin and nothing else — `.web/yarn.lock` is rewritten by
the install the rebuild performs. That is why `.web/.yarnrc.yml` sets
`enableImmutableInstalls: false`: without it the build refuses the changed
lockfile (`YN0028: The lockfile would have been modified by this install, which
is explicitly forbidden`) and the upgrade never goes live. Keep `.web/yarn.lock`
committed: it still pins the transitive tree, and a local `yarn install` brings
its `web-vault` entry back in step.

## Stop conditions

Stop cleanly and report to the user if: a precondition fails; the vault has no
`.md` notes to serve; or (during optional local testing) `yarn install` cannot
reach the public repo or the site shows empty content you cannot resolve by
fixing the vault path.
