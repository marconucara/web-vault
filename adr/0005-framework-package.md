# ADR 0005 — Framework package with a thin config-only consumer and generated deploy functions

## Context

web-vault targets any Markdown vault (`adr/0004-vault-compatibility-target.md`) and
must be adoptable by many vaults without each one carrying a copy of the app. Two
shapes are possible: a **template** the user copies into their repo (owns the code,
must merge upstream changes by hand), or a **framework package** the vault depends
on (owns the code, upgrades by bumping a version) — the Astro/Docusaurus shape.
For a product whose value is the app and its build pipeline, and whose users should
not have to maintain that code, the framework shape is the right boundary.

## Capability statement

web-vault is a **framework package** (`web-vault`) that owns the application source,
the build/content pipeline (`adr/0002-build-time-content-pipeline.md`), and the
React/Vite stack (`adr/0003-stack-react-vite.md`). A vault that adopts it is a
**thin consumer**: it carries **configuration only**, no application code.

- **Config-only boundary.** The consumer directory holds its `wrangler.toml`,
  `public/`, and app config; everything executable lives in the package. The build
  is driven by a Vite config **factory** whose `root` is the package directory
  while `outDir`/`publicDir` point at the consumer's working directory, so the
  package builds *into* the consumer without the consumer hosting the code.
- **Content injection.** Vault content reaches the app through a virtual module
  (`virtual:web-vault-content`) that injects the built `.wv/content.json`, keeping
  the vault's data out of the package and the package's code out of the vault.
- **Deploy functions as build artifacts.** Host functions (e.g. the commit endpoint,
  `adr/0018-edit-commit-via-pages-function.md`) are **not versioned files** in the
  consumer: the build **generates** them from a factory (`makeCommitHandler(config)`)
  into a gitignored output directory. There is no per-function source file to keep
  in the vault, and the generation is deployment-agnostic
  (`adr/0017-deployment-model.md`) — Cloudflare is the first target, not the centre.

## User stories / scenarios

- As a vault owner, I adopt web-vault by depending on the package and keeping only
  config in my repo; I get upgrades by bumping the version, not by merging code.
- As a maintainer, the app and pipeline live in one package, so a fix ships to every
  vault without hand-merges.
- As a vault owner, no host-function source files clutter my vault; the build emits
  them.

## Acceptance criteria

1. The application source, build/content pipeline, and stack live in the `web-vault`
   package; the consumer holds configuration only, no application code.
2. The Vite build runs with `root` in the package and `outDir`/`publicDir` in the
   consumer's working directory, so the package builds into the consumer.
3. Vault content is injected via the `virtual:web-vault-content` virtual module from
   the built content artifact.
4. Host deploy functions are generated by the build from a factory into a gitignored
   output directory, not committed per-function source files, and the mechanism is
   not tied to a single deployment provider.

## Out of scope

- The CLI, setup flow, and distribution channel of the package
  (`adr/0029-cli-setup-and-distribution.md`).
- The concrete commit function and its provider binding
  (`adr/0018-edit-commit-via-pages-function.md`).
